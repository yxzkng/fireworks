# 여의도 불꽃 지도

서울세계불꽃축제 관람 명당별 실시간 혼잡도와 현장 사진 제보를 지도 위에서 함께 보여주는 서비스입니다.
서울시 공공데이터(기지국 기반 인구 추정)와 현장 이용자의 제보를 나란히 놓아,
"지금 어디가 붐비는지"와 "돗자리 깔 자리가 남았는지"를 동시에 판단할 수 있게 만들었습니다.

**https://seoul-fireworks.vercel.app**

## 기술 스택

| 영역 | 사용 기술 |
|---|---|
| Frontend | Vanilla JS · HTML · CSS (프레임워크 없음, 빌드 스텝은 Python 스크립트 하나) |
| Backend | Vercel Serverless Functions (Node.js, ESM) |
| Database | Supabase (Postgres + RLS), Supabase Storage |
| Cache | Vercel KV (Redis) |
| 외부 API | 서울시 실시간 도시데이터 API, 서울시 실시간 지하철 도착정보 API, 카카오맵 JS SDK |
| 프록시 | Cloudflare Workers |
| 배포 | Vercel |

## 구조

하나의 소스에서 두 가지 배포본을 생성합니다.

```
template.html  +  shared.css
      │
      ├─ build.py ─▶ index.html             Claude Artifact 배포판 (한강·여의도 윤곽을 직접 렌더링)
      └─ build.py ─▶ web/public/index.html  Vercel 배포판 (실서비스, 카카오맵)
```

두 배포본은 지도 엔진과 저장소가 달라 HTML/JS는 각자 유지하고, 공통 UI(카드·레일·시트·제보 폼)의
CSS만 `shared.css` 한 곳에서 관리합니다. `index.html`과 `web/public/index.html`은 빌드 산출물이므로
직접 수정하지 않습니다.

```
web/api/congestion.js   서울시 혼잡도 수집·캐싱 (KV 락 + TTL)
web/api/subway.js       지하철 실시간 도착정보 (single-flight 캐싱)
web/api/admin.js        관리자 인증 후 제보 조회/삭제 (service_role 키는 서버에서만 사용)
web/api/config.js       공개 키를 클라이언트에 전달
web/schema.sql          테이블 · RLS 정책 · 신고 함수 · 속도 제한 트리거
proxy/worker.js         서울시 HTTP 전용 API를 위한 HTTPS 프록시
```

## 동시 접속 대응

축제 당일 트래픽이 몰릴 것을 예상하고 부하를 미리 계산했더니, **초기 구조는 약 100명에서 무너지는**
상태였습니다. 원인은 트래픽 양이 아니라 설계 결함이었고, 유료 전환 없이 무료 티어만으로
**약 2,500~3,000명**까지 감당하도록 고쳤습니다. 상세 분석은 [`docs/scaling-plan.md`](docs/scaling-plan.md)에 있습니다.

### 1. N × M × 300행 → 상수

가장 큰 문제는 **제보 1건이 올라올 때마다 접속자 전원이 300행을 다시 읽는** 구조였습니다.
Supabase Realtime 이벤트를 받을 때마다 목록 전체를 재조회했기 때문에, 접속자 N명·분당 제보 M건이면
트래픽이 `N × M × 300행`으로 곱셈 증가했습니다.

실시간 이벤트에는 **새로 들어온 행(`payload.new`)이 이미 담겨 옵니다.** 전체 재조회를 버리고
이 값을 로컬 배열에 병합하도록(INSERT면 추가, UPDATE면 교체, `hidden`이면 제거) 바꿔
전체 조회는 최초 1회만 하게 했습니다.

| 접속자 | 개선 전 egress | 개선 후 |
|---:|---:|---:|
| 100 | 17.3 GB | 0.012 GB |
| 1,000 | 1,728 GB | 0.12 GB |
| 3,000 | 15,552 GB | 0.36 GB |

이때 RLS 정책도 함께 고쳐야 했습니다. Realtime은 **RLS가 SELECT를 막는 행의 이벤트를 조용히 버립니다.**
읽기 정책이 `hidden = false`로 되어 있으면 "신고 3건으로 숨김" UPDATE가 구독자에게 전달되지 않아
다른 사람 화면에는 그 제보가 계속 남습니다. 정책을 열고 필터링은 클라이언트에서 하도록 옮겼습니다.

### 2. 실시간 구독 → 증분 폴링 (동시 연결 한도 제거)

Supabase 무료 티어의 **실시간 동시 연결 200**은 늘릴 수 없는 값이라, 201명째부터는 구독 자체가
실패합니다. 축제 당일에 가장 먼저, 가장 단단하게 막히는 한도였습니다.

연결을 붙들지 않는 방식으로 전환했습니다 — 30초마다 `created_at > 마지막으로 본 시각`인 행만
조회합니다(보통 0~2행). 이걸로 **접속자 수 상한 자체가 사라졌습니다.** 혼잡도 원본이 몇 분 주기로
갱신되므로 30초 지연은 이 서비스에서 문제가 되지 않습니다.
`SYNC_MODE`를 `'realtime'`으로 바꾸면 구독 방식으로 되돌아갑니다(접속이 적을 때는 구독이 더 빠릅니다).

폴링으로 바꾸면서 생긴 부작용도 처리했습니다. 증분 조회는 `created_at`이 바뀌지 않는
"신고로 숨겨진 제보"를 감지하지 못합니다. 그래서 주기적으로 화면의 제보가 숨겨졌는지 확인하는
sweep을 두었는데, 처음 잡은 2.5분 주기에서는 **이 조회 하나가 전체 egress의 73%**를 차지했습니다.
주기를 10분으로 늘리고 검사 대상도 실제 화면에 보이는 80건으로 좁혀 4.73GB → 1.50GB로 줄였습니다.
신고된 제보가 최대 10분 늦게 사라지지만 허용 가능한 지연이라고 판단했습니다.

### 3. 썸네일 분리 — 17배

목록 카드에서 40~68px로 보이는 이미지에 1600px 원본(약 300KB)을 그대로 쓰고 있었습니다.
목록에 최대 57장이 노출되므로 접속 1,000명이면 사진만으로 11.9GB였습니다.

업로드 시점에 **240px 썸네일을 함께 만들어 나란히 저장**하고, 목록과 타임라인은 썸네일만,
원본은 확대해서 볼 때만 불러옵니다.

| | 크기 |
|---|---:|
| 원본 (1280px, q0.82) | 204 KB |
| 썸네일 (240px, q0.72) | **12 KB** |

접속 1,000명 기준 11.9GB → 0.73GB. 원본도 1600px → 1280px로 낮춰 무료 Storage 1GB에
저장 가능한 사진이 약 3,300장 → 4,500장으로 늘었습니다. 사진은 한 번 올라가면 바뀌지 않으므로
캐시 헤더도 1시간에서 1년으로 바꿨습니다.

### 4. 응답 경량화 — 목록 응답 69% 감소

혼잡도 목록 응답에서 **12시간 예측을 제거**했습니다. 예측은 상세 화면에서만 쓰이면서
응답 크기의 65%를 차지했고, 모든 접속자가 주기적으로 받아 가면 그게 전송량의 대부분이 됩니다.
상세를 열 때만 `/api/congestion?area=<이름>`으로 그 장소 것만(1.5KB) 가져와 재사용합니다.

| | 크기 |
|---|---:|
| 목록 응답 (전) | 28,152 bytes |
| 목록 응답 (후) | **8,725 bytes** |

폴링 주기도 60초 → 2분으로 늘렸습니다(서버 수집 주기보다 자주 물어봐야 얻는 게 없음).
응답 축소 3.2배 × 폴링 2배 = 혼잡도 전송량 6.5배 감소.

### 5. 호출 예산 — Cron 없이 캐시 갱신하기

서울시 인증키에는 하루 호출 한도가 있는데, Vercel Hobby 플랜은 **Cron이 하루 1회로 제한**되어
분 단위 폴링 수집이 불가능했습니다. 그래서 **접속자 요청 자체를 트리거로 삼는 방식**으로 바꿨습니다 —
요청이 들어왔을 때 캐시가 만료됐으면 그 요청이 KV에 락을 잡고 대신 갱신합니다.

락을 놓친 동시 요청이 빈손으로 돌아가면 배포 직후나 TTL 만료 순간에 몰린 사람들이 전부 회색 화면을
보게 됩니다. 그래서 락을 놓친 요청은 **락 보유자가 채울 때까지 짧게 폴링하다가 채워진 값을 받아가고**,
그래도 실패하면 하루짜리 stale 사본으로 화면을 채웁니다. 트래픽이 없는 시간대에는 아무도 갱신을
트리거하지 않으므로 호출량이 자연히 줄어듭니다. 지하철 API도 같은 패턴의 single-flight 캐싱을 씁니다.

### 6. 방어 장치

속도 제한을 **두 겹**으로 걸었습니다.

- **브라우저** — 30초 쿨다운. 폼을 열 때 남은 시간을 미리 알려주므로 다 입력하고 나서 막히지 않습니다.
- **DB 트리거** — 한 장소에 10초 안에 5건이 넘으면 INSERT를 거부합니다. 브라우저 제한은 새로고침으로
  우회되므로 **실제 방어는 여기서** 합니다.

`photo_path`가 서버가 만드는 형식인지 DB에서 검사해 임의 경로로 다른 파일을 가리키는 것을 막고,
Storage 버킷에는 용량·MIME 상한을 걸었습니다. 실패 안내도 사유별로 나눴습니다 — 쿨다운,
서버 속도 제한, 사진 용량 초과, 연결 끊김은 이용자가 해야 할 행동이 각각 다르기 때문입니다.

### 결과

| | 감당 인원 | 병목 |
|---|---|---|
| 개선 전 | ~100명 | 제보마다 전원 재조회 |
| 1번 후 | ~3,000명 | 실시간 동시 연결 200 |
| 2번 후 | ~3,000명 | 사진 대역폭 |
| 3·4번 후 | **~2,500명** | Supabase egress |

접속 10,000명 기준으로도 Vercel 대역폭은 32GB(한도 100GB)로 여유가 있어, 남은 병목은 Supabase
egress 한 곳뿐입니다. 그 이상 규모가 필요하면 Supabase Pro로 egress 250GB를 확보하면 됩니다.

## 그 외 설계 메모

- **공공데이터와 제보를 평균 내지 않고 따로 표시합니다.** 기지국 추정은 광역 흐름에, 현장 제보는
  "돗자리 깔 자리 있나" 같은 미시 정보에 강해서, 하나의 숫자로 섞으면 둘 다 흐려집니다.
- **유입/유출 방향** — 지하철 30분 내 승하차를 비교해 "몰려드는 중 / 빠져나가는 중"을 표시합니다.
  혼잡도 숫자만으로는 보이지 않는 정보이고, 종료 후 귀가 러시 판단에 씁니다.
- **지도 다크 처리** — 카카오맵에 공식 다크 타입이 없습니다. CSS `invert` 필터로 반전시키는 방법이
  흔하지만 **지도 이미지 변형은 약관 위반 소지**가 있어(실제 API 차단 사례 존재) 쓰지 않았습니다.
  대신 어두운 반투명 막을 위에 덮어 원본은 그대로 두고 화면만 가라앉힙니다.
- **정렬** — '붐비는 순'은 관람 가능한 곳을 먼저 놓습니다. 그러지 않으면 늘 붐비는 도심 거점이 1위가
  되어 자리 찾는 사람에게 쓸모없는 순서가 됩니다.
- **신고** — RLS에서 `update`를 열면 남의 제보 내용까지 고칠 수 있으므로, `security definer` 함수로
  `flags`만 올릴 수 있게 했습니다. 3건이면 자동으로 가려집니다.
- **GPS를 수집하지 않습니다.** 위치는 이용자가 지도에서 직접 찍은 좌표만 저장됩니다.
- **점진적 성능 저하** — 키가 하나씩 없어도 나머지는 동작합니다. 카카오 키가 없으면 지도만 안내
  문구로 바뀌고 카드는 정상, Supabase가 없으면 제보만 비활성화, 혼잡도 API가 실패해도 제보는
  정상 동작합니다.
